# Admin email templates and staff visibility Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let admin-role staff edit structured transactional email templates, links, and safe button styling, while ensuring only the configured super admin can retrieve the staff list, then deploy the verified changes to production.

**Architecture:** Persist validated overrides in a new additive PostgreSQL table. Admin-only API handlers merge overrides with explicit server defaults and render both HTML and text through the existing email module; system-generated security URLs and delivery behavior remain server-owned. The admin client adds a templates editor and checks super-admin identity for staff access; server authorization remains authoritative.

**Tech Stack:** TypeScript 7, React 19, Vite 8, Vercel serverless API routes, Neon Postgres, Zod 4, existing Tailwind utility styling and current auth/audit helpers.

## Global Constraints

- Use an explicit allowlist of template IDs and fields; reject unknown fields and template names.
- Never accept arbitrary HTML or CSS; escape user text and constrain CTA styling to brand-safe options.
- Verification, reset, staff-invitation, and newsletter-confirmation links must always be generated by server code.
- Never send the staff list to any account other than the configured super admin.
- Mutating template endpoints use the existing same-origin CSRF protection, validation, and audit conventions.
- Production migration must be additive and idempotent; do not run it until local checks are complete and deployment is authorized.
- Do not commit, push, or publish via Git; deploy only because the user explicitly requested production deployment.

## File structure

- `api/_lib/email-templates.ts` — template IDs, built-in content, schema-safe types/defaults, merge/read helpers, and validated override storage access.
- `api/_lib/email-template.ts` — existing shared HTML frame; extend its typed CTA and additional-link rendering while escaping all text and URLs.
- `api/_lib/email.ts` — use override-aware content in every existing email sender, preserving security URL generation, recipients, expiry copy, text output, and delivery semantics.
- `api/_lib/db.ts` — parameterized CRUD functions for template overrides and the super-admin-filtered staff query usage.
- `api/_lib/validation.ts` — Zod schema for template identifier and structured editable fields, link limits/URL checks and style allowlist.
- `api/_lib/routes/admin-email-templates.ts` — authenticated admin-role GET/PUT handler; `requireAdmin`, CSRF, audit, JSON result.
- `api/_lib/routes/admin-staff.ts` — super-admin guard before staff list query; preserve existing super-admin write behavior.
- `api/_lib/routes/index.ts` — register template API endpoints.
- `src/pages/admin/AdminEmailTemplates.tsx` — editor/list selection, add/remove links, CTA label, non-security destination, brand style controls, live preview, save and error feedback.
- `src/components/admin/AdminShell.tsx` — show email templates nav only to `admin`; show staff accounts nav only to super-admin identity.
- `src/SiteShell.tsx` — add protected templates route; gate staff route by super-admin identity in addition to admin role.
- `scripts/migrate-email-templates.mjs` — additive idempotent table migration, following current env loading and Neon conventions.
- `package.json` — migration script entry.
- `scripts/test-staff-roles.mjs` — assert non-super admins get no list (403) and super admin retains list/writes.
- `scripts/test-email-templates.mjs` — test validation, safe rendering/escaping, admin API authorization and persistence using existing local API test conventions.
- `README.md` — document the new admin controls and super-admin-only visibility.
